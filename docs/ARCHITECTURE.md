# Архитектура CLI

`Cli → Core`; `Cli → Data → Core`; `Cli → Infrastructure.Windows → Core`. Все ссылки ProjectReference находятся внутри нового решения. WPF-зависимостей и Desktop FrameworkReference нет. Windows-only TFM сохраняет физические гарантии P/Invoke; перенос на другую ОС не заявлен.

## Повторно используемые уровни

Core содержит исходные модели/результаты/интерфейсы, AuthenticationService/RegistrationService, PasswordSecurity, UserSession, UserStorageService, FileService, ComputerBrowseService, ExternalDocumentService, ExternalFileOperationService, JournalService, DocumentValidator, ZipEngine. Core и Data скопированы побайтно; алгоритмы не переписывались.

Data содержит AppDbContext, SQL Server EF mappings, репозитории и transaction stores. Сохранены версии пакетов 9.0.22, три исходные миграции и snapshot. DI Data остаётся исходным. Windows-библиотека содержит десять файлов адаптеров с единственным изменением namespace.

Composition повторяет сервисную часть WPF App.CreateServices с прежними lifetime. Singleton UserSession корректен для одного интерактивного пользователя одного процесса; этот composition root не предназначен для многопользовательского сервера. ConsoleApplication последовательно ожидает операции и завершает сеанс через AuthenticationService, включая EOF. Меню не заменяет сервисную авторизацию.

## Запуск и конфигурация

Program задаёт UTF-8, составляет DI и запускает StartupCheck. Проверка открывает прежний AppDbContext, использует только SELECT, проверяет точный набор миграций; типы/nullability столбцов, состав PK/индексов, unique/filter/enabled индексы, CHECK и FK. SQL Server timestamp соответствует rowversion; BETWEEN/IN CHECK сравниваются после нормализации SQL Server-представления. Проверка рассчитана на исходную известную схему, не является универсальным доказательством эквивалентности SQL или аудитом произвольных триггеров/ACL/default constraints.

Далее без provisioner/workspace проверяются существование `StorageRoot/Users`, GUID-каталоги известных пользователей и отсутствие каталогов неизвестных пользователей, доступность путей через PersonalStorage.Resolve, существование активных Files и размеры обычных файлов. Никаких audit INSERT probe, marker/lock, автоматического создания Users, синхронизации, cleanup или recovery в preflight нет. Превышение 10000 пользователей/записей даёт отказ для отдельной проверки установки. Неучтённые файлы не усыновляются.

Проверка — снимок; состояние может измениться после неё. В схеме отсутствует DB↔StorageRoot binding. Копия с теми же GUID/путями/размерами может пройти проверку. Полная проверка содержимого по baseline невозможна: такого baseline нет. Отказ не приводит к автоматическому ремонту, неверная конфигурация не создаёт новое хранилище. Несовместимая схема/неизвестные или отсутствующие GUID-каталоги блокируют запуск. Отсутствие/иной размер отдельных Files выводится предупреждением: это может быть следствием прерванного publish до SQL commit. После входа доступны диагностика и явный RecoverAsync; при RecoveryRequired личный браузер предлагает восстановление до загрузки списка. Прежние сервисы проверяют pending/owner/версии, меню ничего не восстанавливает само.

## Конкурентность двух процессов

В FileTransactionStore сохраняется Serializable и блокировка Users по owner через UPDLOCK/HOLDLOCK. WindowsFileStorage удерживает `.sfm-internal/lock` с FileShare.None на пользовательский workspace, проверенные handle/pins, fingerprint и RowVersion. Сервисы имеют внутрипроцессный SemaphoreSlim. SQL сериализация пользователя и физический workspace защищают операции разных экземпляров; semaphore сам по себе между процессами не действует.

В ExternalDocumentStore сохраняется Serializable с блокировкой actor. Для разных actor она не является общей блокировкой пути. Межпроцессная защита внешних операций опирается на `.external-operations/lock`, а редакторов — на `.external-editor/<path-key>/lock` и sharing целевого handle. Editor проверяет наличие pending external operations; operations проверяют pending editor plans. Общая очередь/транзакция между этими протоколами не добавлена. Возможны конфликты/блокировки/deadlock SQL; интерфейс не должен интерпретировать отказ как успех.

Физические проверки/SQL rowversion позволяют отклонять устаревшее сохранение. В WPF нет нового watcher для CLI: после смены программы нужно обновление/перечитывание. CLI перечитывает списки после команд. Метаданные сверяются только по явной команде, восстановление тоже явно.

При crash сохраняются staging/backups/plans и correlation. Сервисы восстановления проверяют факт SQL commit и fingerprint, не удаляют неизвестную замену. SQL+NTFS не образуют единую распределённую транзакцию; сбой питания, чужая запись тем же OS token и привилегированный локальный злоумышленник не покрыты обещанием полной устойчивости. Внешний save остаётся in-place для сохранения ACL/identity; backup содержит plaintext.

Тесты нескольких экземпляров сервисов и Windows lock проверяют важные гонки, но реальный одновременный запуск WPF+CLI, остановка процессов между каждой фазой и полная матрица межпроцессных гонок не выполнялись. Эксплуатационный режим до такой приёмки — последовательные сеансы. Новая глобальная блокировка только в CLI не смогла бы заблокировать неизменённый WPF, поэтому ложная гарантия не вводилась.

## Безопасность и UI

Файловые операции идут только через исходные сервисы; прямые File/Directory вызовы нового слоя ограничены read-only preflight конфигурации/метаданных. GUID личного объекта получается из авторизованного списка; сам сервис всё равно проверяет owner. Внешний прямой путь проходит прежние политики, исключает личный Storage, reparse/hardlinks/UNC/ADS и не повышает права Windows.

ConsoleUi нейтрализует управляющие/format символы для защиты вывода терминала, включая ANSI escape. AuditListItem извлечён из исходного файла VM как независимый record; описание журналов строится по разрешённым кодам без raw Details/исключений/содержимого документов. CLI не пишет пароли в журнал. Маскировка не устраняет неизбежное пребывание строк паролей в памяти .NET.

Редактор хранит буфер и версию отдельно, SaveAsync/ValidateAsync/ReloadAsync остаются сервисными. Конфликт не очищает буфер. После сохранения новая версия подтверждается чтением; при неопределённости повторная запись требует перечитывания. Ctrl+C отменяет активный CancellationToken; окончательная компенсация ожидается. Нет force-kill и фоновых задач.
